# CLI-first command center plan

## Objective

Review the two supplied videos as untrusted evidence, prioritize the Omarchy 4
video, and apply only the smallest lesson that advances Dream House: make the
accepted operator registry directly usable from a keyboard-only CLI.

## Admitted delta

Add one no-dispatch module entry point with four operations:

1. list the shared command inventory;
2. search it using typed terms;
3. show only assigned key bindings; and
4. prepare an unauthorized, hash-bound request from explicit arguments.

Human-readable output and JSON must derive from the same registry. No separate
menu database, fuzzy-search dependency, TUI framework, global hotkey binding,
shell completion installer, controller, or action dispatcher is admitted.

## Pruned Omarchy features

Desktop tiling, global window management, themes, wallpapers, dictation,
recording, reminders, Docker panels, OS settings, plugins, update management,
factory reset, and system-wide shortcuts remain outside this slice. They may be
reconsidered only when a concrete Dream House workflow needs them.

## Second-video disposition

The software-rendering video is relevant to graphics and low-level learning,
not to the current operator surface. It contributes no implementation feature.
Its only reusable principle is to understand a lower layer without rebuilding a
mature abstraction in production.

## Acceptance

- Every displayed action comes from `builtin_registry()`.
- Search and key listings are deterministic and keyboard-only.
- `prepare` retains explicit-target and typed-argument checks.
- No command can dispatch, authorize, write native state, or bind a hotkey.
- Focused CLI tests and the complete House suite pass.
- Independent read-only review finds no consequential gap.

## Model advisory

Case type: `app_delivery`; Terra/medium-equivalent implementation is sufficient.
Escalate only if live dispatch, global shortcuts, plugin loading, or authority
enters scope.
